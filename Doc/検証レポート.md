# AI自動レビュー・ユニットテスト生成システム 検証レポート

**作成日:** 2026年8月31日
**実評価日:** 2026年8月26日〜27日
**評価対象コミット:** `093f391fd79340ce86f067a40fe23faa13137eb0`
**評価対象:** AI Review Jenkins デモ版
**参照資料:** [評価設計書](評価設計書.md)、[評価結果](評価結果_2026-08-26.md)

## 概要

本レポートは、GitLab、Jenkins、Claude Code、Webhook受信サーバ、Workerを連携したAI自動レビュー・ユニットテスト生成システムについて、機能成立性、AI出力品質、信頼性、セキュリティ、非機能特性を検証した結果をまとめたものである。

実GitLab・Jenkins・Claude Codeを用いたデモでは、AIレビュー、修正案の確認と承認、修正コミット、ユニットテスト生成、Jenkinsテスト、C0/C1通知までの主要技術要素が動作した。このため、デモとしての技術実証は成立した。

一方、正解付き評価データを用いたAI品質の統計評価は未実施である。指摘再現率、指摘適合率、F1、修正正解率、生成テスト有効率について、現時点では有効な数値を提示できない。したがって、本レポートは主にシステム完成度と実行可能性の検証結果であり、AI性能の優位性を統計的に証明するものではない。

## 1. 評価指標

### 1.1 AIレビュー品質

| 指標 | 定義・計算方法 | 採用理由 | 今回の測定状況 |
|---|---|---|---|
| 指摘再現率（Recall） | `正解指摘と一致したAI指摘数 / 正解指摘数` | 既知不具合をどれだけ見逃さず指摘できたかを評価する | 未測定 |
| 指摘適合率（Precision） | `人間が有効と判定したAI指摘数 / AI指摘数` | 誤指摘や不要な指摘の少なさを評価する | 未測定 |
| F1 | `2 × Precision × Recall / (Precision + Recall)` | 見逃しの少なさと誤指摘の少なさを一つの値で比較する | 未測定 |
| 位置精度 | 正しいファイルかつ対象行±5行以内に投稿された指摘の割合 | GitLab Discussionが修正対象を正しく示しているかを評価する | 1件で一致を確認。統計値なし |
| パッチ適用率 | `git apply --checkに成功したパッチ数 / パッチ付き指摘数` | AIが生成した修正案の構文的な適用可能性を評価する | 1件で適用成功。統計値なし |
| 修正正解率 | `不具合を解消し既存テストを壊さなかったパッチ数 / 評価パッチ数` | 修正案が実際に問題を解決したかを評価する | 未測定 |
| 不要変更率 | `要求外ファイルまたは無関係行を変更した評価数 / 全評価数` | AI修正の局所性と安全性を評価する | 評価した承認コミット1件では0件 |

コードレビューは、同じ問題を異なる文章で表現できる意味的な評価である。このため、単純な文字列一致によるaccuracyは主指標にしない。正解付き不具合集合と人間評価を用いたPrecision、Recall、F1を主指標とする。

### 1.2 ユニットテスト生成品質

| 指標 | 定義・計算方法 | 今回の測定状況 |
|---|---|---|
| バグ再現テスト率 | `修正前に失敗し、修正後に成功した生成テスト数 / 対象不具合数` | 未測定 |
| テスト有効率 | `コンパイル可能かつ3回同じ結果となった生成テスト数 / 生成テスト数` | 未測定 |
| C0カバレッジ | 実行されたステートメント数 / 全ステートメント数 | 62.5% |
| C1カバレッジ | 実行された分岐数 / 全分岐数 | 40.9% |
| カバレッジ寄与 | `生成後カバレッジ - 生成前カバレッジ` | 生成前の値がないため未算出 |

BLEUは参照コードとの表面的な語句一致を測る指標であり、意味的に同等な別実装を低く評価する可能性がある。そのため、本検証では採用しない。生成テストについては、コンパイル、再現性、修正前後の成否、カバレッジ寄与を評価する。

### 1.3 システム・非機能指標

| 指標 | 計算・判定方法 | 結果 |
|---|---|---|
| デモ要素成功率 | 成功した主要デモ要素数 / 全主要デモ要素数 | 8 / 8、100% |
| 自動テスト成功率 | Pass数 / 実行テスト数 | 99 / 99、100% |
| 実装コード行カバレッジ | pytestによるline coverage | 81% |
| 評価ケース判定 | Pass / Fail / Blocked / Not Run | 11 / 7 / 2 / 26 |

| Webhook応答時間 | ngrok経由30件のp50、p95、最大値 | 22.1ms、52.2ms、397.3ms |

| 秘密値露出 | ログ・MRコメントと設定済み秘密値の一致件数 | 0件 |

## 2. 評価方法

### 2.1 評価環境

| 項目 | 条件 |
|---|---|
| GitLab評価対象 | GitLab.com上の評価プロジェクト MR !13 |
| Jenkins | デモ用Jenkinsコンテナ、Build/Test Pipeline |
| AI実行 | 認証済みClaude Code CLI |
| Agentイメージ | `sha256:0b792f1f8acf1f3d601a0939d80ad26628c0edbc526298cbc6cf8197dc4d88a1` |
| Jenkinsイメージ | `sha256:35c6649ffb362eed4e0e50d4d7f0982527f7aa22cb7378c2f3e33b69b675f070` |
| サービス状態 | docker、jenkins、webhook、workerがhealthy |
| Webhook | Merge Request events、Note events、SSL verificationを有効化 |
| 外部公開 | 評価中のみngrokを起動し、終了後に停止 |

Claude Codeの具体的なモデル名・バージョン、temperature相当の生成条件、seedは実行証跡に記録されていない。このため、同一条件でのAI出力再現性は保証できない。

### 2.2 使用データ

実環境E2EではMR !13を使用し、次のデータを評価対象とした。

- Flutter/DartプロジェクトのMR差分
- JenkinsのBuild/Lint結果
- AIが生成したレビュー指摘R2と修正パッチ
- `/ai apply R2`、`/ai approve R2`による承認操作
- AIが生成したユニットテスト
- Jenkinsテスト結果とLCOVから算出したC0/C1
- 不正Webhook token、不正Jenkins callback token
- ngrok経由の無効Push Hook 30件

[評価設計書](評価設計書.md)で計画したD-01〜D-09の独立評価MRと、AI品質評価用の最低20 MRは準備できていない。今回のAI出力確認は少数事例による技術実証である。

### 2.3 評価手順

1. 評価対象コミットをAgentコンテナへ読み取り専用でマウントし、pytestとline coverageを実行した。
2. GitLab MRから`/ai review`を実行し、AI出力、DB、GitLab Discussionの対応を確認した。
3. AIが不正JSONを返した場合に、検証処理がエラーを検知して再生成することを確認した。
4. `/ai apply R2`前後でMR SHAが変化しないことを確認した。
5. `/ai approve R2`後に、承認対象ファイルだけがコミットされたことを確認した。
6. `/ai test`からテスト生成、GitLabコミット、Jenkinsテスト、C0/C1通知までを確認した。
7. 不正token、無効イベント、応答時間、秘密値露出、ジョブキュー解放を確認した。
8. 評価設計書の46ケースに対してPass、Fail、Blocked、Not Runを記録した。

## 3. ベースライン比較

### 3.1 自動テスト基盤の改善前後

リポジトリに残る2026年8月15日の検証値をbaselineとし、2026年8月26日〜27日の評価値と比較した。

| 指標 | Baseline（2026-08-15） | 評価時（2026-08-26〜27） | 差分 |
|---|---:|---:|---:|
| 自動テストPass数 | 57 | 99 | +42件 |
| 自動テスト成功率 | 100% | 100% | 0ポイント |
| line coverage | 72% | 81% | +9ポイント |

テスト数は57件から99件へ73.7%増加し、line coverageは9ポイント上昇した。これはWebhook、GitLab連携、Jenkins callback、AI出力解析などのテスト追加と実装範囲拡大を示す。

ただし、前後でテスト対象コードとテストケース構成が異なるため、この比較だけで不具合検出能力が同じ割合で改善したとは解釈できない。システム回帰テストの整備状況を示す参考比較として扱う。

### 3.2 カバレッジ目標との比較

| 指標 | 目標 | 実測 | 目標との差 |
|---|---:|---:|---:|
| C0 | 80.0% | 62.5% | -17.5ポイント |
| C1 | 70.0% | 40.9% | -29.1ポイント |

生成テストを含むJenkinsテスト自体はSUCCESSだったが、C0/C1はいずれも目標未達となり、Jenkins判定はUNSTABLEだった。特にC1の差が大きく、条件分岐や境界値を補うテスト生成に改善余地がある。

生成前カバレッジを記録していないため、この数値からAI生成テストによる純粋な改善量は算出できない。

### 3.3 他手法との比較

次の比較は実施していない。

- AIを使わない人手レビューとの指摘数、所要時間、見逃し率の比較
- 利用者が自由入力したプロンプトと、チーム共通プロンプトとのPrecision、Recall、F1比較
- 単純プロンプトと、現在のコンテキスト制御・JSON検証・再試行を含む方式との比較
- Claude Codeと他モデルの比較

したがって、現時点では「共通プロンプト方式が他手法より高精度である」とは結論できない。本システムで確認できた価値は、共通プロンプトによる実行経路の統一、AIレビュー過程のGitLabへの記録、人間承認境界を含む一連の処理が技術的に成立したことである。

今後は同一の正解付きMRを使用し、自由プロンプト、共通プロンプト、人手レビューを同じ条件で比較する。指摘Precision、Recall、F1、作業時間、プロンプト作成時間を記録する必要がある。

### 4.2 結果の考察

主要なデモ要素は8項目すべて成功した。特に、AIの提案を`apply`だけではブランチへ反映せず、`approve`後に限定してコミットする境界を確認できた点は、人間とAIの責任分界という企画上の目的に合致する。

AIの1回目の出力は不正JSONだったが、形式検証と再試行により2回目で回復した。生成AIの出力揺らぎを前提とした防御が実環境で機能した事例である。ただし、1事例だけでは回復率を評価できない。

テスト生成からJenkins実行までは完走したが、C0/C1は目標未達だった。テストを生成できることと、十分な分岐・境界条件を網羅できることは別であり、生成プロンプトへの未実行箇所入力、既存テストとの差分分析、生成後の品質評価が必要である。

評価ケース全体では、判定を実施できた18件のうち11件がPassで成功率61.1%だった。ただし、Not Runが26件と全体の56.5%を占める。データ未準備や未実装分岐が多く、製品受入レベルの完成度を示す結果ではない。

## 5. 失敗例・限界

### 5.1 確認された失敗例

| 事象 | 結果 | 影響 |
|---|---|---|
| AIが不正JSONを返した | 1回目は`Unterminated string`、2回目で回復 | 再試行がなければレビュー登録不能 |
| 全Discussion Resolve | GitLab Hookの`changes`に`blocking_discussions_resolved`がなく、自動再レビューが起動しなかった | 手動で`/ai review`と`/ai test`が必要 |
| AI修正承認後の経路 | Build成功後、再レビューを行わずテスト生成へ直接遷移した | 企画当初の再レビュー経路と異なる |
| UNIT_TEST_GENタイムアウト | Claude CLIが2回タイムアウトしFAILED | 再実行操作が必要 |
| GitLab API障害 | DNS解決失敗により失敗通知が欠落 | 利用者が失敗を認識できない可能性 |
| カバレッジ通知 | C0/C1値のみで、目標値、達成可否、未実行箇所を表示しなかった | 改善箇所を判断しにくい |
| Webhook重複配信 | delivery IDの保存と重複排除が未実装 | ジョブ、コメント、コミットが重複する可能性 |

### 5.2 現時点の限界

1. **AI品質を統計評価できていない**
   正解付きデータ、最低20 MR、人間評価者2名による評価を実施していないため、Precision、Recall、F1、修正正解率、テスト有効率は算出できない。

2. **ベースラインが限定的である**
   比較できたのはリポジトリの自動テスト数とline coverageのみである。自由プロンプト、人手レビュー、他モデルとの比較はない。

3. **生成テストの寄与を分離できない**
   生成前カバレッジを記録していないため、生成テストによるC0/C1増分を算出できない。

4. **AI実行条件の再現性が不足している**
   モデルの完全な識別子、バージョン、実行ごとの入力ハッシュ、実行回数が十分に記録されていない。

5. **現行デモには運用条件がある**
   全Discussion Resolve後の自動再レビューは使用できず、手動操作が必要である。タイムアウトや通知失敗時にも運用者の再実行・確認が必要となる。

6. **セキュリティ・耐障害性評価が未完了である**
   bodyサイズ制限、レート制限、project ID許可リスト、Webhook delivery IDによる重複排除、通知再試行が未実装である。

7. **評価規模が小さい**
   AIレビュー、パッチ適用、生成テストはいずれも少数事例であり、対象言語・プロジェクト・不具合カテゴリが変わった場合の一般化性能は確認できていない。

## 結論

本システムは、共通プロンプトによるAIレビュー、レビュー記録、修正承認、テスト生成、Jenkins検証を一つのMR上で実行する技術デモとして成立した。主要デモ要素は8/8成功し、自動テストは99/99成功、line coverageは81%だった。

一方、AI性能を示すPrecision、Recall、F1などは未測定であり、他手法に対する品質面・工数面の優位性はまだ確認できていない。現時点の結論は「主要機能の技術的実現性を確認した」であり、「AI品質または生産性向上を統計的に実証した」ではない。

次回評価では、正解付きMR、生成前後のカバレッジ、共通プロンプトと自由プロンプトの比較、レビュー・プロンプト作成の所要時間を記録し、本企画の目的である属人化低減、レビュー記録、工数削減を定量評価する。
