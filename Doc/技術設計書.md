# CI/CDとAIエージェントを統合した自動コードレビュー・ユニットテスト生成システム 技術設計書

**バージョン：** 0.3（技術選定・AI設計サマリー追加）
**作成日：** 2026年5月11日
**最終更新日：** 2026年9月1日

---

## 1. 目的

本書は、AI自動レビュー・ユニットテスト生成システムの技術的な実装方針・構成・インタフェース仕様を定義する。

コードレビューとユニットテスト生成に使用するプロンプト、入力コンテキスト、出力形式、実行条件をリポジトリで一元管理し、利用者ごとのプロンプト品質への依存を減らす。また、AIの指摘、修正案、承認、生成テスト、CI結果をGitLab MRへ記録することで、AI利用を個人内で完結させず、チームで追跡可能な開発プロセスとして運用する。

言語・フレームワーク非依存のコアアーキテクチャと、プロジェクト固有のスキルファイル・設定を分離することで、**多様なプロジェクトへの展開を容易にする設計**とする。

### 2. モデル選定理由

現行実装は、すべてのAIジョブでClaude Sonnetを既定モデルとする。主な選定理由は以下のとおりである。

- コード差分、既存実装、CIログ、カバレッジを組み合わせた複合的な推論に適し、レビューとテストコード生成の両方を1モデルで扱える。
- Opus系の最上位モデルと比較してコストと応答時間を抑えつつ、セキュリティや非同期処理を含むコードレビューに必要な品質を確保しやすい。
- Haiku系の軽量モデルと比較して、複数ファイルの関係、Flutter/Dart固有の非同期・Widgetの制約、最小パッチの作成で安定性を期待できる。
- Claude Code CLIを経由することで、差分だけで判断できない場合に、隔離された作業ツリー内の関連ファイルを読み取って確認できる。
- 日本語の指摘文と原文の識別子・コードを併記する出力要件に対応しやすい。

学習済み基盤モデルに対する追加学習やファインチューニングは行わず、タスク別プロンプトと決定的な後処理を組み合わせる手法を採用する。学習データの作成・更新を不要にし、対象リポジトリの規約変更にプロンプトで追従できるためである。

### 3. 工夫点

#### 3.1 精度向上のための入力設計

- `REVIEW`と`RE_REVIEW`では、変更ファイルに限定した`git diff --unified=3`、Build結果、Lint結果を同時に与える。コードだけでは検出できないコンパイルエラーや静的解析結果を判断根拠にできる。
- 初回レビュー後のコミットSHAをチェックポイントとして保存し、再レビューでは前回確認済み以降の差分を対象にできる。
- `UNIT_TEST_GEN`では差分に加えてカバレッジ未達行を`path:line,...`形式で与え、未テストの分岐を優先させる。
- WorkerはJenkinsが実際にビルドしたコミットSHAをcheckoutする。キュー待ち中にブランチ先頭が更新されても、CI結果とAI入力のソースを一致させる。

#### 3.2 プロンプト設計

- レビュー、ビルドエラー診断、パッチ再構成、テスト生成ごとに役割と出力契約を分離する。不要な指示の干渉を抑える。
- レビュー観点を「コード品質」「バグリスク」「セキュリティ」「Dart固有」に固定し、`Future`の未`await`や`BuildContext`の非同期越えなど、参照Flutterプロジェクトで重要な障害パターンを明示する。
- レビュー出力を`findings`配列を持つJSONに固定し、各指摘にファイル、行範囲、日本語説明、before/after、unified diffを要求する。指摘がない場合も`{"findings": []}`とし、後続処理の分岐を一意にする。
- テスト生成では正常系、境界値、分岐網羅、バグ再現の優先順位に加え、`MaterialApp`、ローカライゼーション、アセット、画面サイズ後始末などWidget Testで発生しやすい失敗を具体的に禁止・指定する。
- プロンプト本文はコマンドライン引数ではなく標準入力でCLIへ渡す。プロンプトやソースコードがプロセス一覧に露出するリスクを下げる。

#### 3.3 出力品質と安全性の確保

- CLIが成功終了してもレビューJSONが不正な場合は、エスケープ方法と「JSONのみ」という制約を追加して再推論する。既定はCLI実行失敗の再試行を含め2回である。
- 後処理は生JSONだけでなく、誤って付与されたMarkdown fenceや前後の説明文からも対象JSONを回復する。その後、必須構造と文字列・整数型を検証し、不正データをDBに保存しない。
- AIに指摘IDを採番させず、サーバーがMRごとに`R1`から連番を付与する。パッチのSHA-256もサーバー側で計算し、承認時にDBの本文と再照合する。
- `RE_REVIEW`では適用済み指摘と同一行範囲に重なる指摘を保存対象から除外し、対応済み問題の重複投稿を抑制する。
- 保存済みパッチが先行修正と競合した場合のみ、AIに最新ブランチ向けの最小パッチを再構成させる。再構成後も、元パッチと同じファイル集合であることをサーバーで検証する。
- `REVIEW`、`RE_REVIEW`、`UNIT_TEST_GEN`、`PATCH_REBASE`ではClaude Codeの`Write`、`Edit`、`NotebookEdit`を禁止する。AIが作業ツリーを直接変更せず、構造化出力を検査した後にサーバー側がコミットする。
- CLI呼び出しには既定600秒のタイムアウト、30ターン上限、5 MiBの出力サイズ上限を設け、ハングアップや過大出力がWorker全体を占有し続けることを防ぐ。

### 4. データの扱い

#### 4.1 入力データ

| データ | 内容 | AIへの入力 |
|---|---|---|
| MRメタデータ | project ID、MR IID、source/target branch、repository URL、commit SHA、変更ファイル一覧 | MR ID、差分対象の決定、作業ツリー準備に使用 |
| ソース差分 | 対象ブランチまたは前回レビューのチェックポイントと`HEAD`間のunified diff | レビュー、ビルドエラー診断、テスト生成の主入力 |
| CI結果 | Build/Lintのstatusとlog | `REVIEW` / `RE_REVIEW` / `BUILD_FIX`の判断根拠 |
| カバレッジ | LCOVから得たファイル別の未達行 | `UNIT_TEST_GEN`の優先対象 |
| AI指摘 | 説明、対象ファイル・行、保存済みパッチ、SHA-256、状態 | パッチ確認・競合時の再構成、重複指摘除外 |
| 運用コマンド | GitLabコメントの`/ai apply|approve|reject|test|review`と指摘ID | 実行ジョブと対象指摘の決定に使用 |

Webhook Secret、GitLab Token、Jenkins Token、AnthropicのAPI Key/OAuth Tokenは認証にのみ使用し、プロンプト本文に含めない。一方、ソース差分、必要に応じてCLIが読み取る関連ファイル、CIログ、カバレッジ情報は外部のClaudeサービスへ送信される。機密コードを扱う運用では、Anthropic側の契約・データ保持ポリシーと送信可否を別途確認する。

#### 4.2 前処理

1. `X-Gitlab-Token`を定数時間比較で検証し、Webhook本文をJSONとして解析した後、Merge Request/Noteイベントから必要項目を取り出す。本文サイズの上限は現行実装になく、製品化時の追加対策とする。
2. `project_id/mr_id`ごとの分離ワークスペースへ対象リポジトリをclone/fetchし、Jenkinsの対象コミットSHAをcheckoutする。repository URLはHTTP(S)のみ許可し、認証情報の埋め込みとGitLab以外のhostを拒否する。
3. `changed_files`をpathspecとして`git diff --unified=3`を実行し、MRと無関係なファイルをプロンプトから除く。差分生成に失敗した場合はAIを実行せずジョブを失敗とする。
4. CI結果を`status`/ログの定型形式に、未達行を`path:line,...`形式に整形し、タスク別システム指示と結合する。
5. AI出力はJSONパース、型検証、Markdown fence除去、ファイルパスマーカ分割など、出力種別ごとの後処理を行う。

#### 4.3 学習・推論での使い方

- 本システムはユーザーコード、MR、指摘履歴をモデルの追加学習に使用しない。RAG用の埋め込み生成やベクトルDBへの登録も行わない。
- 各ジョブは都度の推論であり、MR固有のデータは実行時コンテキストとしてのみ使用する。過去のAI会話履歴に依存せず、差分・CI結果・DBの確定状態から毎回プロンプトを再構成する。
- レビュー結果は型検証後にSQLiteへ保存し、GitLab MRに投稿する。生成テストはファイルマーカごとに分割してsource branchへコミットし、Jenkinsで実行する。AI出力だけで成功とせず、ビルド、テスト、カバレッジの実績で検証する。
- DBはDocker named volume、リポジトリの作業コピーは分離ワークスペースに保持する。保持期間や削除ジョブは現行実装では定義していないため、製品化時に運用ポリシーとして追加する。

### 5. 代替案と比較

| 検討案 | 利点 | 採用状況・採用しなかった理由 |
|---|---|---|
| Claude Opusを全ジョブで使用 | 複雑な推論でより高い品質を期待できる | コストと応答時間が増え、MRごとに複数回実行するCI用途では過剰と判断した。現行はSonnetを品質とコストの中間案として採用 |
| Claude Haikuをタスク別に併用 | 定型的な処理のコストとレイテンシを低減できる | 軽量なコメント生成には有効だが、現行のAIジョブはいずれもコード判断を含む。実測評価とタスク別品質基準が未整備のため未採用。環境変数によるタスク別モデル上書きは実装済み |
| Anthropic Messages API / SDKを直接利用 | `max_tokens`、Prompt Caching、構造化メッセージ、モデルIDを厳密に制御できる | 対象リポジトリの読み取りツール、OAuthログイン、ツール実行ループを自前実装する必要があるため現行デモでは未採用。14.2節のPrompt Cachingは将来構想であり、現行CLI経路ではアプリケーションから制御していない |
| 差分だけでなく変更ファイル全文や`git diff -W`を常時送信 | 定義、関数全体、前後関係の見落としを減らせる | トークン量、コスト、機密コードの外部送信範囲が増えるため常時利用は未採用。現行は3行文脈の差分を主入力とし、必要な場合にCLIがワークスペースを読み取る。14.3節のハイブリッド方式は将来構想 |
| RAG（埋め込み+ベクトルDB） | 大規模リポジトリから類似実装や規約を検索できる | 現行の参照プロジェクトは差分とローカル検索で対応でき、インデックスの更新、アクセス制御、古いコードの誤検索を増やす複雑性に見合わないため未採用 |
| 専用モデルのファインチューニング | 組織固有の指摘傾向や出力形式を学習できる | 十分な正解付きデータがなく、規約や対象コードの変更への追従コストも高い。プロンプトと検証ロジックの方が更新・監査しやすいため未採用 |
| 静的解析・ルールベースレビューだけを使用 | 決定的で高速、実行コストが低く、誤検知の再現も容易 | ビジネスロジック、複数箇所の関係、修正意図に依存する問題を検出しにくい。未採用ではなく、JenkinsのBuild/LintをAIの前段に置き、AIと相補的に使用 |
| AI生成パッチの自動適用 | 修正までのリードタイムを最小化できる | 誤修正や意図外の変更が直接ブランチに入るリスクがある。`/ai apply`で差分を確認し、`/ai approve`後にのみハッシュ照合済みパッチをコミットするHuman-in-the-loop方式を採用 |

## 3. データモデル

### 3.1 指摘（Finding）

```sql
CREATE TABLE findings (
    id          TEXT NOT NULL,     -- AI指摘: R1, R2, ...（MRごとに採番）
    mr_id       TEXT NOT NULL,
    source      TEXT NOT NULL,     -- AI
    status      TEXT NOT NULL,     -- OPEN / APPLIED / REJECTED
    author      TEXT,
    file_path   TEXT,
    line_start  INTEGER,
    line_end    INTEGER,
    description TEXT,
    suggestion  TEXT,              -- before/after形式の修正提案（任意）
    fix_patch   TEXT,              -- 指摘IDに紐づくunified diff（任意）
    fix_patch_sha256 TEXT,         -- 提案外変更混入防止用のパッチハッシュ
    created_at  DATETIME,
    updated_at  DATETIME,
    PRIMARY KEY (mr_id, id)
);
```

指摘IDはMR単位で採番し、各MRの最初の指摘を`R1`とする。同じMRで再レビューした場合は既存の最大番号の次から採番し、別MRでは再び`R1`から開始する。

修正パッチは `.patch` ファイルとして保存せず、`findings.fix_patch` にunified diff文字列を直接保持する。  
`fix_patch_sha256` は同じレコードに保持し、`/ai approve ID` 時にDB上のpatch本文とハッシュを照合して提案外変更の混入を防ぐ。

### 3.2 状態遷移

GitLab DiscussionsのClose（Resolve）状態はDBで管理しない。AI指摘の処理状態はDBを正とし、
`/ai approve`または`/ai reject`によってOPENなAI指摘が0件になったかを判定する。

```
OPEN
 ├─▶ APPLIED（/ai approve 実行 → 指摘IDに紐づく修正パッチをハッシュ確認してコミット）
 └─▶ REJECTED（/ai reject 実行）
```

> **現行デモの全AI指摘対応後フロー：**
> OPENなAI指摘が0件になるとBuild/Lintを再実行し、成功後は再レビューを省略してユニットテスト生成へ進む。
>
> **製品化目標：**
> GitLab Discussionsの全ResolveをAPIで確実に検知し、Build/Lint後に`RE_REVIEW`を実行する。GitLab.comの実WebhookではResolve時に`blocking_discussions_resolved`が含まれなかったため、現行デモではこの経路を自動化対象外とする。

### 3.3 MR状態

複数MRを並行処理するため、MR状態はMR単位で保持する。

| 状態 | 定義 |
|---|---|
| `Opend` | MR作成直後。ビルド/静的解析エラー時も維持 |
| `レビュー中` | AIレビューまたは再レビュー実行中 |
| `レビュー指摘対応中` | AI/人間レビュー指摘への対応待ち |
| `ユニットテスト生成中` | 指摘解消後、ユニットテスト生成・実行中 |
| `テスト確認中` | 生成テスト結果やカバレッジ確認待ち |
| `マージ待ち` | レビュー・テスト完了後、マージ可能 |
| `Closed` | MRがマージまたはクローズ済み |

ビルドエラー時は `Opend` のまま `BUILD_FIX` を実行する。静的解析エラー時は `Opend` のままMRコメントで通知し、`/ai review` でレビュー開始可能とする。

### 4.4 ジョブキュー・エージェント稼働管理

#### 設計方針

CLIエージェントは1プロセスで動作するため、複数のMRから同時にイベントが届いた場合に排他制御が必要。  
Webhook受信時にジョブをDBに登録し、常駐ワーカーが順次処理する。  
**エージェントの稼働状態はインメモリ変数を使わず、DBの `job_queue` テーブルで判定する。**

#### CLIタスク完了の検知

ワーカーは `asyncio.create_subprocess_exec` でCLIを起動し、`proc.communicate()` でプロセス終了を待機する。  
プロセスが終了した時点でCLIタスクの完了を検知し、DBのジョブステータスを更新する。

```python
async def run_agent(prompt: str) -> tuple[int, str]:
    """CLIエージェントを起動し、終了まで待機して結果を返す"""
    proc = await asyncio.create_subprocess_exec(
        "claude", "--prompt", prompt,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE
    )
    stdout, stderr = await proc.communicate()  # プロセス終了まで待機
    return proc.returncode, stdout.decode()    # 終了コードで成否判定
```

#### ジョブキューテーブル（DB）

```sql
CREATE TABLE job_queue (
    job_id      TEXT PRIMARY KEY,   -- UUID
    mr_id       TEXT NOT NULL,
    event_type  TEXT NOT NULL,      -- BUILD_FIX / REVIEW / APPLY / APPROVE / RE_REVIEW / UNIT_TEST_GEN
    payload     TEXT NOT NULL,      -- JSON（Webhookペイロード等）
    status      TEXT NOT NULL,      -- WAITING / PROCESSING / DONE / FAILED
    created_at  DATETIME NOT NULL,
    started_at  DATETIME,
    completed_at DATETIME
);
```

| event_type | 発生タイミング |
|---|---|
| `BUILD_FIX` | ビルド失敗 → ビルドエラーのみを対象に修正提案 |
| `REVIEW` | MR作成後の静的解析成功、または `/ai review` → AIレビュー実行 |
| `APPLY` | `/ai apply <ID>` コマンド受信 → 修正案差分をMRコメントに提示 |
| `APPROVE` | `/ai approve <ID>` コマンド受信 → 保存済み修正パッチをコミット |
| `RE_REVIEW` | `blocking_discussions_resolved: true`を受信し、全Resolve確認後のBuild/Lintが成功した場合。実GitLab.comでは未成立 |
| `UNIT_TEST_GEN` | 全AI指摘対応後のBuild/Lint成功、`RE_REVIEW`指摘なし、または`/ai test` |

#### エージェント稼働状態の判定（DB参照）

インメモリ変数は使わず、DBの `PROCESSING` 件数で判定する。  
プロセス再起動後も正確な状態を復元できる。

```python
async def is_agent_busy() -> bool:
    """PROCESSING 中のジョブが1件でもあれば BUSY と判定"""
    result = db.query(
        "SELECT 1 FROM job_queue WHERE status='PROCESSING' LIMIT 1"
    )
    return len(result) > 0

async def recover_stale_jobs():
    """起動時: PROCESSING のまま残ったジョブを FAILED に戻す"""
    db.execute(
        "UPDATE job_queue SET status='FAILED' WHERE status='PROCESSING'"
    )
```

#### 処理フロー

```
[Webhook受信]
    │
    ▼
ジョブをjob_queueに登録（status: WAITING）
    │
    ▼
is_agent_busy() でDB確認
    │
    ├─ False（IDLE）──▶ 即時ジョブ取得・status: PROCESSING に更新・処理開始
    │
    └─ True（BUSY） ──▶ キューに積んだまま返却（ワーカーが完了後に拾う）

[CLIプロセス終了を proc.communicate() で検知]
    │
    ▼
returncode で成否判定
    ├─ 0     → status: DONE に更新
    └─ 0以外 → 1回だけリトライ。再失敗時は status: FAILED に更新・MRにエラーコメント投稿
    │
    ▼
次の WAITING ジョブを取得
    ├─ あり ──▶ 次ジョブ処理開始
    └─ なし ──▶ 待機（次のWebhook受信まで）
```

#### 同一MR内の順序制御

同一 `mr_id` のジョブが PROCESSING 中は後続を待機させる（レビュー・コミット・再レビューの競合を防止）。

```python
async def can_process(mr_id: str) -> bool:
    """同一MRで処理中のジョブがあれば待機させる"""
    result = db.query(
        "SELECT 1 FROM job_queue WHERE mr_id=? AND status='PROCESSING'",
        (mr_id,)
    )
    return len(result) == 0
```

## 5. Jenkinsパイプライン設計

### 5.1 ビルドパイプライン（MR作成時）

ビルドと静的解析は分離する。ビルド失敗時は静的解析をskipし、ビルドエラーのみを対象に `BUILD_FIX` ジョブを登録する。静的解析失敗時はAIレビューへ進まず、MR状態はOpendのままMRコメントで通知する。静的解析失敗後は `/ai review` でレビューを手動開始できる。

```groovy
pipeline {
    agent any
    stages {
        stage('Checkout') { ... }
        stage('Build') {
            steps {
                // ${BUILD_COMMAND}（project.yaml / 環境変数 BUILD_COMMAND から取得）
                // 失敗時は BUILD_FIX ジョブを登録し、Lint/AIレビューはskip
            }
        }
        stage('Lint') {
            steps {
                // ${LINT_COMMAND}（同上 LINT_COMMAND）
                // 失敗時はMRコメントで通知し、AIレビューはskip
            }
        }
        stage('AI Review') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                // CLIエージェント呼び出し
                // 指摘をDBに保存・GitLabにコメント投稿
            }
        }
    }
}
```

### 5.2 テスト実行パイプライン（ユニットテスト生成後）

生成済みユニットテストを実行し、テスト結果とカバレッジをMRへ投稿するパイプライン。  
テスト実行失敗時は1回だけリトライする。カバレッジ目標未達時の追加生成ループは自動実行しない。
目標値は Jenkins パラメータで上書き可能で、デフォルトは環境変数（§9.2）から取得する。

#### 処理フロー

```
Checkout
  │
  ▼
既存テスト実行 + lcov カバレッジ取得
  │
  ├─ テスト実行失敗 ──▶ 1回リトライ ──▶ 再失敗時はMRへ投稿（完了）
  │
  ▼
C0 / C1 を LCOV から計算
  │
  ├─ 目標達成 ──────────────────────────────▶ 結果をMRへ投稿（完了）
  │
  └─ 目標未達 ──────────────────────────────▶ 未達箇所と結果をMRへ投稿（完了）
```

> **バグ検出時：** テストは正常に実行されたが生成テストでバグを検出した場合は、修正案提示フローへ戻る。

#### Jenkinsfile

```groovy
pipeline {
    agent any
    parameters {
        string(name: 'MR_IID',    defaultValue: '',
               description: 'GitLab MR IID（Webhook受信サーバから渡す）')
        string(name: 'C0_TARGET', defaultValue: "${env.COVERAGE_C0_TARGET ?: '80'}",
               description: 'C0（ステートメント）カバレッジ目標 (%)')
        string(name: 'C1_TARGET', defaultValue: "${env.COVERAGE_C1_TARGET ?: '70'}",
               description: 'C1（ブランチ）カバレッジ目標 (%)')
    }
    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('テスト実行・カバレッジ計測') {
            steps {
                script {
                    def c0Target = params.C0_TARGET.toInteger()
                    def c1Target = params.C1_TARGET.toInteger()

                    try {
                        sh "${env.TEST_COMMAND}"  // 環境変数 TEST_COMMAND（例: flutter test --coverage --branch-coverage）
                    } catch (err) {
                        echo "テスト実行失敗 → 1回リトライ"
                        try {
                            sh "${env.TEST_COMMAND}"
                        } catch (retryErr) {
                            env.TEST_EXEC_FAILED = 'true'
                            currentBuild.result = 'UNSTABLE'
                        }
                    }

                    if (env.TEST_EXEC_FAILED != 'true') {
                        def finalCov = parseLcov(env.COVERAGE_REPORT_PATH ?: 'coverage/lcov.info')
                        env.FINAL_C0 = finalCov.c0.toString()
                        env.FINAL_C1 = finalCov.c1.toString()
                        env.COVERAGE_MET = (finalCov.c0 >= c0Target && finalCov.c1 >= c1Target).toString()
                    }
                }
            }
        }
        stage('結果をMRへ投稿') {
            steps {
                sh """
                    python src/gitlab_reporter.py \\
                      --mr-id   ${params.MR_IID} \\
                      --c0      ${env.FINAL_C0} \\
                      --c1      ${env.FINAL_C1} \\
                      --c0-target ${params.C0_TARGET} \\
                      --c1-target ${params.C1_TARGET} \\
                      --met     ${env.COVERAGE_MET} \\
                      --test-exec-failed ${env.TEST_EXEC_FAILED ?: 'false'}
                """
            }
        }
    }
}

// ─── 共通ライブラリ関数 ────────────────────────────────────────────────────────

/** LCOV ファイルから C0（ステートメント）と C1（ブランチ）カバレッジを計算する */
def parseLcov(String lcovPath) {
    def lines = readFile(lcovPath).readLines()
    long totalLines = 0, hitLines = 0
    long totalBranches = 0, hitBranches = 0

    lines.each { line ->
        if (line.startsWith('DA:')) {
            // DA:<行番号>,<実行回数>
            totalLines++
            if (line.tokenize(',')[1].toInteger() > 0) hitLines++
        } else if (line.startsWith('BRDA:')) {
            // BRDA:<行番号>,<ブロック>,<分岐番号>,<実行回数 or '-'>
            totalBranches++
            def count = line.tokenize(',')[3]
            if (count != '-' && count.toInteger() > 0) hitBranches++
        }
    }
    return [
        c0: totalLines     > 0 ? (hitLines     * 100 / totalLines).toInteger()     : 100,
        c1: totalBranches  > 0 ? (hitBranches  * 100 / totalBranches).toInteger()  : 100
    ]
}

/** 目標未達の行・分岐を {"lib/foo.dart": [42, 55]} 形式で抽出する */
def extractUncovered(String lcovPath, int c0Target, int c1Target) {
    def lines = readFile(lcovPath).readLines()
    def result = [:]
    def currentFile = ''

    lines.each { line ->
        if (line.startsWith('SF:')) {
            currentFile = line.substring(3)
            result[currentFile] = []
        } else if (line.startsWith('DA:') && currentFile) {
            def parts = line.tokenize(',')
            if (parts[1].toInteger() == 0) {
                result[currentFile] << parts[0].substring(3).toInteger()
            }
        }
    }
    return result.findAll { k, v -> !v.isEmpty() }
}
```

#### カバレッジ種別（C0 / C1）

| 種別 | 内容 | LCOV 対応行 | LCOV 出力対応例 |
|---|---|---|---|
| C0（ステートメント） | 全実行可能行のうち1回以上実行された割合 | `DA:` 行 | Flutter / Python(pytest-lcov) / Jest / JaCoCo変換 |
| C1（ブランチ） | 全分岐のうち1回以上実行された割合（if/else・switch 等） | `BRDA:` 行 | Flutter / Jest / JaCoCo変換 |

> **注：** C2（条件カバレッジ）は多くのLCOV出力に含まれないため対象外とする。LCOV形式にエクスポートできるツール（JaCoCo → lcov、pytest-lcov 等）であれば `parseLcov()` はそのまま流用できる。

### 5.3 Jenkins結果コールバック

Jenkinsパイプラインは完了時にDocker内部ネットワーク上の
`POST /internal/jenkins/result`へ結果を返す。外部公開はせず、
`X-Internal-Token`と`JENKINS_CALLBACK_TOKEN`を定数時間比較して認証する。

| パイプライン結果 | Webhook受信サーバの処理 |
|---|---|
| Build失敗 | `BUILD_FIX`ジョブ登録 |
| Build成功・Lint失敗 | MRへ静的解析失敗コメントを投稿 |
| Build/Lint成功 | `REVIEW`ジョブ登録 |
| 全AI指摘対応後のBuild/Lint成功（`POST_RESOLUTION`） | `UNIT_TEST_GEN`ジョブを直接登録 |
| 全Resolve検知後のBuild/Lint成功（`RE_REVIEW`） | `RE_REVIEW`ジョブ登録 |
| Test完了 | テスト結果とC0/C1をMRへ投稿 |

Webhook受信サーバはキュー登録または結果投稿の完了後にHTTP 202を返す。

## 6. CLIエージェント（Claude）連携仕様

### 6.1 呼び出し方式

- 常駐Workerが`asyncio.create_subprocess_exec`でClaude Code CLIを起動する
- プロンプトはコマンドライン引数ではなく標準入力で渡し、標準出力をAI出力として受け取る
- モデルは`CLAUDE_MODEL_<EVENT_TYPE>`、`CLAUDE_MODEL`、`sonnet`の優先順位で決定する
- 既定の最大ターン数は30、タイムアウトは600秒、失敗時の最大試行回数は2とする

```bash
claude --print --model sonnet --max-turns 30 \
  --disallowedTools Write Edit NotebookEdit < prompt.txt
```

`--disallowedTools`は`REVIEW`、`RE_REVIEW`、`UNIT_TEST_GEN`、`PATCH_REBASE`に付与する。`BUILD_FIX`はプロンプト上で直接編集を禁止し、原因と修正案のMarkdown出力のみを求める。

### 6.2 プロンプト設計

#### AIレビュー用プロンプト（概要）

```
以下のdiffを解析し、コード品質・バグ・セキュリティ上の問題を指摘してください。
各指摘には以下を含めてください：
- 指摘ID（R1, R2, ...）
- 対象ファイル・行番号
- 指摘内容（日本語）
- 修正提案（説明は日本語、before/after形式）

出力形式：JSON
```

#### 修正パッチ出力（概要）

```
指摘ID: {ID}
指摘内容: {description}
対象コード: {before}

レビュー時に上記指摘に対する修正パッチも生成してください。
出力形式：unified diff
```

#### ユニットテスト生成用プロンプト（概要）

```
以下のFlutter/Dartコードの修正内容に対して、
① バグ再現テスト（flutter_testを使用、修正前に失敗するケース）
② 正常・境界テスト（分岐網羅・エッジケース）
を生成してください。
テスト種別：Unit Test（必須）・ Widget Test（UI変更時）
カバレッジ未達箇所: {uncovered_lines}
修正内容: {diff}
```

### 6.3 出力形式（AIレビュー）

```json
{
  "findings": [
    {
      "id": "R1",
      "file": "src/foo.py",
      "line_start": 42,
      "line_end": 45,
      "description": "NullPointerExceptionが発生しうる",
      "suggestion": {
        "before": "return obj.value",
        "after": "return obj.value if obj else None"
      },
      "fix_patch": "--- a/src/foo.py\n+++ b/src/foo.py\n..."
    }
  ]
}
```

AI出力の`id`は信頼せず、保存時にサーバーがMR単位で再採番する。`fix_patch_sha256`もAIに生成させず、受信した`fix_patch`からサーバーが計算する。

### 11.2 エージェント定義（AGENT.md）

#### 11.2.1 AIレビューエージェント（`ai-reviewer.agent.md`）

**役割：** MRのdiffを受け取り、コード品質・バグ・セキュリティ問題を検出してJSON形式で指摘を出力する。

```markdown
---
name: ai-reviewer
description: >
  AIコードレビューを実行する。MRのdiffを受け取り、コード品質・バグ・セキュリティ問題を
  JSON形式の指摘リストとして出力する。レビュー・静的解析・差分チェックが必要な場合に使用。
tools: [read, search]
user-invocable: false
---

あなたはFlutter/Dartコードの専門レビュアーです。
渡されたdiffを解析し、以下の観点で問題を検出してください。

## レビュー観点

1. **コード品質**: 命名規則・関数分割・単一責任の原則・重複コード
2. **バグリスク**: NullPointerException・型不一致・境界値・非同期処理の抜け
3. **セキュリティ**: 入力値バリデーション不足・秘密情報のハードコード・OWASP Top 10
4. **Dart固有**: `late`変数の未初期化リスク・`Future`の未await・`BuildContext`のAsync越え利用

## 制約

- DO NOT コードを実行・変更する
- DO NOT diff以外のファイルを読み込む（contextに渡された範囲のみ参照）
- ONLY 指摘の検出と出力に専念する
- `description` と修正提案の説明文は必ず日本語で出力する（コード、ファイルパス、識別子は原文のまま保持する）

## 出力形式

必ずJSON形式で出力すること。指摘がない場合は `"findings": []` を返す。

```json
{
  "findings": [
    {
      "id": "R1",
      "file": "<ファイルパス>",
      "line_start": <開始行>,
      "line_end": <終了行>,
      "description": "<指摘内容>",
      "suggestion": {
        "before": "<修正前コード>",
        "after": "<修正後コード>"
      },
      "fix_patch": "<unified diff>"
    }
  ]
}
```
```

`id`と`fix_patch_sha256`はAI出力を信頼せず、サーバーが保存時に採番・計算する。

```

-<修正前コード>
+<修正後コード>
 <変更なし行>
```
```

import 'package:{パッケージ名}/{テスト対象ファイル}';

void main() {

      // arrange
      // act
      // assert
    });
  });
}
```
```

  await someProcess();
  if (!mounted) return;
  Navigator.of(context).pop();

- テスト名は「条件」と「期待結果」を含む動詞句で記述する（例: `'returns null when input is empty'`）
- テスト内では `print` を使用せず、`expect` で結果を検証する

#### カバレッジ目標

カバレッジ目標は環境変数（§9.2）でプロジェクト共通のデフォルトを設定し、Jenkinsパラメータで実行毎に上書きできる。

| 種別 | 環境変数 | デフォルト値 | 内容 |
|---|---|---|---|
| C0 | `COVERAGE_C0_TARGET` | `80` | ステートメントカバレッジ（実行行割合） |
| C1 | `COVERAGE_C1_TARGET` | `70` | 分岐カバレッジ（if/switch 等の分岐網羅割合） |

> 目標値の辺り目安：新規コードは C0 80% 以上・ C1 70% 以上を推奨する。担当者が `.env` で調整し、第三者検演等の局面では Jenkins パラメータで一時的に増減できる。

## 14. トークン使用量の最適化（将来構想を含む）

Claudeのコスト削減とレート制限（TPM/RPM）への抵触回避を目的とした設計方針を定める。現行実装はClaude Code CLI、`git diff --unified=3`、Sonnetの既定利用である。14.2節のPrompt Caching、14.3節の入力コンテキスト自動切替、14.4節のHaiku併用、14.5節の`max_tokens`個別制御は将来構想である。

### 14.1 基本方針

| 方針 | 概要 |
|---|---|
| プロンプトキャッシング | 変化しない部分をキャッシュし、キャッシュヒット率を最大化する |
| 差分のみ渡す | フルファイルを渡さず `git diff` 出力のみをコンテキストとする |
| モデル使い分け | タスクの複雑さに応じてHaiku / Sonnetを選択する |
| 出力フォーマット圧縮 | JSONのみ要求し、説明文・前置きを排除する |

---

### 14.2 プロンプトキャッシング（Prompt Caching、将来構想）

Claude APIのPrompt Caching機能（`cache_control: {"type": "ephemeral"}`）を活用し、MR間で共通する固定コンテキストをキャッシュする。

#### キャッシュ構造（メッセージブロック順）

```
[Block 1] システムプロンプト + AGENT.md 定義内容    ← cache_control 付与（最長有効）
[Block 2] コーディング規約・チェックリスト（12節相当）← cache_control 付与
[Block 3] MR固有の diff・カバレッジ情報              ← キャッシュなし（毎回変わる）
```

- キャッシュ有効期間：5分（Claude デフォルト）
- 同一MR内の複数コマンド（REVIEW → APPROVE → RE_REVIEW）ではBlock 1・2 のキャッシュヒットが期待できる

#### 実装例（Python SDK）

```python
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=4096,
    system=[
        {
            "type": "text",
            "text": AGENT_SYSTEM_PROMPT,          # AGENT.md 内容
            "cache_control": {"type": "ephemeral"}
        },
        {
            "type": "text",
            "text": CODING_CONVENTIONS,           # 12節コーディング規約
            "cache_control": {"type": "ephemeral"}
        }
    ],
    messages=[
        {"role": "user", "content": diff_content} # MR固有 diff（キャッシュなし）
    ]
)
```

### 14.3 入力コンテキストの最小化（将来構想）

フルファイルを渡すとトークン数が数倍に膨らむが、差分のみでは変更箇所に関連する既存コードが欠落するリスクがある。

> **⚠️ 差分のみ渡す場合の欠落リスク：**  
> 変更された関数の呼び出し元・クラスのフィールド定義・別ファイルの `override` 先など、  
> 差分に現れない箇所が影響を受けていても、レビュアーには見えない。

これに対し、**タスク種別とファイルサイズを組み合わせたハイブリッド戦略**を採用する。

#### タスク種別によるオーバーライドルール（最優先）

| event_type | コンテキスト戦略 | 理由 |
|---|---|---|
| `UNIT_TEST_GEN` | **`-W` 固定**（≤ 500行）または **フルファイル**（≤ 200行） | バグ再現テストの生成には変更関数の全体像が必須。前後数行では関数シグネチャ・戻り値・ガード節が欠落する |
| `REVIEW` / `RE_REVIEW` / `APPROVE` | 下記ファイルサイズ基準に従う | レビュー・修正パッチ確認は差分周辺があれば判断可能 |

#### ファイルサイズ基準（REVIEW系タスク）

| 変更ファイルの行数 | 戦略 | 理由 |
|---|---|---|
| ≤ 200行 | **フルファイル送付** | ファイルが小さく、全文渡してもトークンコストが低い |
| 200〜500行 | **関数コンテキスト拡張 (`-W`)** | 変更を含む関数全体を展開し、周辺の定義を補う |
| > 500行 | **差分 + `-U20` 拡張コンテキスト** | 関数全体が大きすぎる場合は前後20行に留める |

#### 関数コンテキスト拡張（`-W`）

`-W` / `--function-context` オプションを使用すると、変更ハンクを含む**関数全体**がコンテキストとして展開される。前後3行のみより格段に文脈が補われる。特に `UNIT_TEST_GEN` では、テスト対象の引数・戻り値・例外仕様がすべて見えることが品質に直結する。

```bash
# 変更を含む関数全体を展開（UNIT_TEST_GEN および 200〜500行ファイルのREVIEW系）
git diff -W origin/main...HEAD \
  -- ':(exclude)*.lock' \
  -- ':(exclude)pubspec.lock' \
  -- ':(exclude)*.g.dart' \
  -- ':(exclude)*.freezed.dart'
```

#### ファイルサイズ・タスク種別判定の実装例

```python
def build_diff_context(changed_files: list[str], event_type: str) -> str:
    """タスク種別とファイルサイズに応じてコンテキスト戦略を切り替える"""
    contexts = []
    for file_path in changed_files:
        line_count = count_lines(file_path)

        if event_type == "UNIT_TEST_GEN":
            # テスト生成は関数全体が必須
            if line_count <= 200:
                contexts.append(f"# {file_path} (full)\n" + read_file(file_path))
            elif line_count <= 500:
                contexts.append(run(f"git diff -W origin/main...HEAD -- {file_path}"))
            else:
                # 500行超は -W だと出力が膨大になるためフルファイルを断念し -U30 で代替
                contexts.append(run(f"git diff -U30 origin/main...HEAD -- {file_path}"))
        else:
            # REVIEW / APPROVE 系
            if line_count <= 200:
                contexts.append(f"# {file_path} (full)\n" + read_file(file_path))
            elif line_count <= 500:
                contexts.append(run(f"git diff -W origin/main...HEAD -- {file_path}"))
            else:
                contexts.append(run(f"git diff -U20 origin/main...HEAD -- {file_path}"))

    return "\n\n".join(contexts)
```

#### 除外対象ファイル（共通）

```bash
# 自動生成ファイルはいずれの戦略でも除外する
EXCLUDE_PATTERNS=(
  ':(exclude)*.lock'
  ':(exclude)pubspec.lock'
  ':(exclude)*.g.dart'
  ':(exclude)*.freezed.dart'
)
```

| 除外対象 | 理由 |
|---|---|
| `pubspec.lock` | 自動生成・依存解決ファイル（レビュー対象外） |
| `*.g.dart` / `*.freezed.dart` | コード生成ファイル（手動編集なし） |
| `*.lock` 全般 | パッケージロックファイル |

### 14.4 モデル選択（タスク別、将来構想）

タスクの複雑さに応じてモデルを使い分け、不必要に高性能なモデルを使用しない。

| event_type | 推奨モデル | 根拠 |
|---|---|---|
| `REVIEW` | `claude-sonnet-4-5` | セキュリティ解析・複合的判断が必要 |
| `APPROVE` | `claude-sonnet-4-5` | 保存済みパッチの整合性確認が必要 |
| `RE_REVIEW` | `claude-sonnet-4-5` | 再レビューもフルレビューと同等 |
| `UNIT_TEST_GEN` | `claude-sonnet-4-5` | テンプレートベースだが品質重視 |
| エラーコメント生成 | `claude-haiku-4-5` | 定型文生成のみ・複雑な判断不要 |

CLIオプションでモデルを指定する。

```bash
# レビュー・修正系
claude --print --model claude-sonnet-4-5 < prompt.txt

# 定型コメント生成等の軽量タスク
claude --print --model claude-haiku-4-5 < error_comment_prompt.txt
```

### 14.5 出力フォーマット圧縮（`max_tokens`個別制御は将来構想）

JSON以外の出力（説明文・前置き・後書き）を排除するようプロンプトで明示的に指示する。

#### プロンプト末尾への追加指示（共通）

```
## 出力制約
- JSONのみ出力すること。説明文・前置き・後書きは一切含めない。
- 指摘がない場合は {"findings": []} のみ返すこと。
- コードブロック（```）で囲まない。生のJSONを返すこと。
```

#### `max_tokens` 上限の設定

| タスク | max_tokens | 根拠 |
|---|---|---|
| `REVIEW` | 4,096 | 指摘10件 × 400トークン程度を想定 |
| `APPROVE` | 2,048 | 保存済みパッチ確認は通常小さい |
| `UNIT_TEST_GEN` | 8,192 | テストファイル全体を生成するため大きめに確保 |
| エラーコメント生成 | 512 | 定型文のみ |

### 14.6 トークン使用量のモニタリング

APIレスポンスの `usage` フィールドをジョブ完了時にDBへ記録し、コスト管理・最適化の継続改善に活用する。

#### job_queue テーブルへの追加カラム

```sql
ALTER TABLE job_queue ADD COLUMN input_tokens        INTEGER;
ALTER TABLE job_queue ADD COLUMN output_tokens       INTEGER;
ALTER TABLE job_queue ADD COLUMN cache_read_tokens   INTEGER;  -- キャッシュヒット分（割引対象）
ALTER TABLE job_queue ADD COLUMN cache_write_tokens  INTEGER;  -- キャッシュ書き込み分
```

#### 記録実装例

```python
async def run_agent(prompt: str, model: str) -> tuple[int, str, dict]:
    proc = await asyncio.create_subprocess_exec(
        "claude", "--model", model,
               "--output-format", "json",   # 使用量をJSON出力に含める
               "--prompt", prompt,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE
    )
    stdout, stderr = await proc.communicate()
    result = json.loads(stdout.decode())

    usage = {
        "input_tokens":       result.get("usage", {}).get("input_tokens", 0),
        "output_tokens":      result.get("usage", {}).get("output_tokens", 0),
        "cache_read_tokens":  result.get("usage", {}).get("cache_read_input_tokens", 0),
        "cache_write_tokens": result.get("usage", {}).get("cache_creation_input_tokens", 0),
    }
    return proc.returncode, result.get("content", ""), usage
```

## 15. プロジェクトアダプタ設計

多様なプロジェクトへ導入できるよう、**コア（言語非依存）** と **アダプタ（言語・FW固有）** を分離する。

### 15.1 設計方針

| 層 | 内容 | 変更頻度 |
|---|---|---|
| コア | Webhook受信・ジョブキュー・CLI呼び出し・GitLab API・DB | 変更なし（全プロジェクト共通） |
| アダプタ | ビルド/Lint/テストコマンド・レビュー観点・テストテンプレート | 導入先ごとに差し替え |

### 15.2 アダプタ構成（対象リポジトリ側）

導入先リポジトリのルートに `.ai-review/` ディレクトリを配置する。

```
<導入先リポジトリ>/
├── .ai-review/
│   ├── project.yaml           # プロジェクト設定（必須）
│   └── skills/                # 言語固有スキル（§11 の .claude/skills/ 相当）
│       ├── code-review/
│       │   ├── SKILL.md       # レビュー観点・チェックリスト
│       │   └── checklists/
│       └── unit-test/
│           ├── SKILL.md       # テスト生成規約・テンプレート
│           └── templates/
└── ...（通常のプロジェクトファイル）
```

### 15.3 project.yaml スキーマ

```yaml
# .ai-review/project.yaml
language: flutter              # 必須：言語識別子
build_command: flutter build   # 必須：ビルドコマンド
lint_command: flutter analyze  # 必須：Lint コマンド
test_command: flutter test --coverage --branch-coverage  # 必須：行・分岐カバレッジ出力込み
coverage_format: lcov          # 任意：デフォルト lcov（現在 lcov のみサポート）
coverage_report_path: coverage/lcov.info  # 任意：レポートファイルパス
```

Webhook受信サーバ起動時に `project.yaml` を読み込み、§9.2 の対応する環境変数へ注入する。`.env` の値が未設定の場合のフォールバックとして機能する。

### 15.4 言語別対応状況

| 言語 / FW | test_command 例 | カバレッジ形式 | 対応状況 |
|---|---|---|---|
| Flutter (Dart) | `flutter test --coverage --branch-coverage` | LCOV | ✅ リファレンス実装 |
| Python | `pytest --cov --cov-report=lcov` | LCOV (pytest-lcov) | 🔧 スキルファイル要追加 |
| TypeScript / Node | `jest --coverage --coverageReporters=lcov` | LCOV | 🔧 スキルファイル要追加 |
| Java / Kotlin | `./gradlew test jacocoTestReport`（lcov変換別途） | LCOV (JaCoCo→lcov) | 🔧 スキルファイル要追加 |

> **重要：** `parseLcov()` 関数（§5.2）はLCOV形式に準拠した出力であれば言語を問わず動作する。各言語のカバレッジツールをLCOV出力に設定するだけでコア側の変更は不要。
