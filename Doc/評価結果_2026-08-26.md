## 1. 総合判定

デモ判定は「**適合（技術実証済み、運用条件あり）**」。

GitLab WebhookからJenkins、Worker、Claude Code、GitLab Discussion/コミット、
生成テストとカバレッジ通知までの主要技術要素が実環境で動作した。
また、人間のapprove前にブランチを変更しない承認境界も確認できた。
そのため、「デモで主要機能が技術的に実現可能であることを示す」という目的に対しては適合と判定する。

一方、[評価設計書](評価設計書.md)の本番受入相当の基準をそのまま適用した場合は
「不適合」である。次の項目はデモ後の製品化課題として扱う。

- Discussionを全ResolveしたGitLabイベントから再レビューが起動しない。
- AI修正の承認後は、再Build後に再レビューせずテスト生成へ直接進む。
- Webhook delivery IDの保存と重複排除がない。

## 4. L3の主な実績

### 手動テスト生成

- MR !13への /ai test からUNIT_TEST_GENジョブ0d9c4589-d095-47f2-b013-7f80bf71b627が起動し、DONEとなった。
- 生成コミット98cea48a57190d7ffada0c6b5caab19e3b086742が作成された。
- Jenkins ai-review-test #8が実行され、テストはSUCCESS、C0 62.5%、C1 40.9%となった。
- 目標C0 80%、C1 70%未達のためJenkinsはUNSTABLEとなった。
- MRには実行結果とC0/C1が投稿されたが、目標値、達成可否、未実行箇所は表示されなかった。

### レビューJSON再試行

- /ai review からREVIEWジョブe9ca3c68-2b98-47ae-a6bd-bc6f1cf189acが起動した。
- 実Claudeの1回目はUnterminated stringの不正JSONだった。
- JSON検証がこれを検出し、生出力をログへ出さず2回目を実行した。
- 2回目は成功し、R2がOPENで保存され、対象行Discussionが作成された。
- DBのパッチSHA-256は実パッチと一致し、DiscussionのID、パス、行、説明、パッチもDBと一致した。

### apply / approve

- /ai apply R2はジョブ1e9c8244-6534-4f88-beea-d9a5828ddaefでDONEとなった。
- apply前後でMR SHAは不変で、R2もOPENのままだった。
- /ai approve R2はジョブ2b6cd984-a005-4b38-aa52-70d6764fc401でDONEとなった。
- 承認コミット7c8ba93228646a1fcf7b884636d98e512962704dはtest/state/auth_state_test.dartだけを変更し、R2はAPPLIEDとなった。
- APPLIED後のapprove再送では新規ジョブや重複コミットが作成されなかった。

### 全Discussion Resolve後

- GitLabはResolve操作後にMerge Request Hookを配信し、WebhookはHTTP 200を返した。
- 実payloadのchangesにはupdated_atしかなく、実装が待つblocking_discussions_resolvedは含まれなかった。
- そのため再BuildとRE_REVIEWは起動しなかった。
- R2承認後のJenkins ai-review-build #28はSUCCESSだったが、POST_RESOLUTIONからUNIT_TEST_GENへ直接進み、RE_REVIEWを実行しなかった。

### タイムアウトと通知

- 自動登録されたUNIT_TEST_GENジョブ1815e437-23f3-4118-8888-9ada4494797cは、Claude CLIが2回タイムアウトしてFAILEDとなった。
- 終了後はWAITING 0件、PROCESSING 0件となり、キューは解放された。
- 失敗通知時にGitLab向けDNS解決が一時失敗し、MR通知が欠落した。
- 通知自体の再試行や後続通知キューはない。GitLab APIはその後HTTP 200へ回復した。

## 7. 検出事項

| ID | 優先度 | 内容 | 対応方針 |
|---|---|---|---|
| DEF-L3-001 | P0 | Resolve Hookで再レビューが起動しない | Discussion/Note Hookを契機にDiscussions APIで全Resolveを再確認 |
| DEF-L3-002 | P0 | approve後にRE_REVIEWを省略 | Build/Lint成功後にRE_REVIEWを登録し、指摘0件時だけテスト生成 |
| DEF-L3-003 | P0 | Webhook delivery IDの重複排除がない | 冪等キー、DB一意制約、保持期間を実装 |
| DEF-L3-004 | P1 | カバレッジ未達通知にtarget/met/uncoveredがない | callback schemaとMR表示を拡張 |
| DEF-L3-005 | P1 | GitLab障害で失敗通知が永続欠落する | 通知をアウトボックスまたは再試行キューへ分離 |
| DEF-L3-006 | P1 | body、レート、project ID制限がない | 外部公開前に制限とテストを追加 |
| DEF-L3-007 | P1 | ngrok経由で業務外パスにも到達可能 | Traffic Policyでパスとメソッドを限定 |

Jenkins ai-review-build #28はSUCCESSだったが、Build約3,047秒、Lint約797秒、合計約3,850秒を要した。総処理時間の受入基準がないため不具合とはせず、性能観測値として記録する。

## 8. デモ実施時の運用条件

1. デモ開始前にComposeサービスとngrokを起動し、GitLab Hookの到達を確認する。
2. 全Discussion Resolve後の自動再レビューは使用せず、デモ操作者が /ai review を投稿する。
3. テスト生成がタイムアウトした場合は、キューがFAILEDになったことを確認後、/ai test を再投稿する。
4. デモ終了後はngrokを停止する。

上記の操作で、MRレビュー、修正承認、テスト生成、Jenkins実行、
カバレッジ確認のデモを完了できる。
