# CloneからAIレビュー実行までの初回導入手順

この手順は、新しいPCで本リポジトリをCloneし、GitLabのMerge Request（MR）を
起点にAIレビューが投稿される状態までを構築するためのものです。標準構成は次のとおりです。

```text
GitLab MR
  -> HTTPS Webhook（ngrok）
  -> webhook
  -> Jenkins Build / Lint
  -> worker（Claude Code）
  -> GitLab Discussion
```

この手順では、GitLab.com、Claude Pro/Maxの対話ログイン、Flutter Webプロジェクトを
利用する構成を例にします。社内GitLabを利用する場合の違いは「社内GitLabでの変更点」を
参照してください。

## 1. 事前に用意するもの

- Windows 10/11とWSL 2上のUbuntu
- Git
- Docker EngineとDocker Compose v2、またはDocker DesktopのWSL連携
- メモリ4 GB以上、空き容量50 GB以上（推奨）
- AIレビュー対象のGitLabプロジェクト
- 対象プロジェクトへDeveloper以上でアクセスできるGitLabアカウント
- Claude Pro/Maxアカウント、またはAnthropic Console APIキー
- GitLab.comからWebhookを受ける場合は、インストール・認証済みのngrok

初期値のBuild/Lint/TestコマンドはFlutter向けです。

```text
Build: flutter pub get && flutter build web
Lint:  flutter pub get && flutter analyze --no-fatal-infos
Test:  flutter pub get && flutter test --coverage
```

他の言語・フレームワークを対象にする場合は、起動前に`.env`の`CI_IMAGE`、
`BUILD_COMMAND`、`LINT_COMMAND`、`TEST_COMMAND`、`COVERAGE_REPORT_PATH`を変更します。

## 2. WSL 2とDockerを確認する

PowerShellでWSLのバージョンを確認します。

```powershell
wsl -l -v
```

対象Ubuntuの`VERSION`が`1`の場合は、ディストリビューション名を指定してWSL 2へ
変換します。

```powershell
wsl --set-version Ubuntu 2
```

以降のコマンドはWSLのUbuntuターミナルで実行します。Docker Desktopを使う場合は、
Docker Desktopを起動して対象UbuntuのWSL Integrationを有効にしてください。

```bash
docker version
docker compose version
docker info
```

3コマンドがエラーなく完了することを確認します。

## 3. リポジトリをCloneする

Dockerのファイルアクセス性能と権限問題を避けるため、`/mnt/c/...`ではなくWSL側の
ファイルシステムへCloneします。

```bash
cd ~
git clone <このリポジトリのURL> ai-review
cd ai-review
./scripts/check-jenkins-host.sh
```

最後に`Jenkins host prerequisites passed.`と表示されれば、ホストの準備は完了です。

## 4. GitLabトークンと共有シークレットを用意する

### 4.1 GitLabアクセストークン

GitLabでAIレビュー専用のProject Access Tokenを作成します。Project Access Tokenは個人
アカウントに依存せず、アクセス先を対象プロジェクトだけに制限できるため推奨です。

対象プロジェクトの`Settings` → `Access tokens`で、次の値を指定します。

- Role: `Developer`
- Scope: `api`、`read_repository`
- Expiration date: 組織の運用ルールに従って設定

トークンの作成には、対象プロジェクトのMaintainerまたはOwner権限が必要です。
GitLab.comでProject Access Tokenを作成するにはPremiumまたはUltimateプランが必要です。
GitLab Self-Managedでは、管理者やグループの設定によって作成が制限されている場合があります。

`api`はMR情報の取得、コメント・Discussionの投稿、承認済み修正と生成テストのコミットに、
`read_repository`はJenkinsからのGit Cloneに使います。Project Access Tokenの`api` scopeには
Git over HTTPSの権限が含まれないため、`read_repository`も必ず選択してください。本実装は
修正適用にGitLab Commits APIを使い、Git pushは行わないため、`write_repository`は不要です。

Project Access Tokenの作成時に、`project_<project_id>_bot_<random_string>`形式のBot
ユーザーが生成されます。このユーザー名は、後述するJenkins Credentialへ設定できます。
Git over HTTPSの認証では任意の空でないユーザー名も使用できますが、識別しやすいBot
ユーザー名の使用を推奨します。

Project Access Tokenには次の制約があります。

- 作成したプロジェクト以外にはアクセスできません。
- Fork元など、別プロジェクトにあるMRソースブランチはClone・更新できません。
- AIがコミットするソースブランチが保護されている場合は、BotユーザーのRoleとブランチ
  ルールでpush相当の操作を許可するか、未保護の作業ブランチを使います。
- 有効期限が切れる前に新しいトークンへ更新する必要があります。

Project Access Tokenを利用できない場合は、専用BotアカウントのPersonal Access Tokenも
使用できます。同じく`api`と`read_repository`を選択し、対象プロジェクトへDeveloper以上で
参加させてください。個人の通常利用アカウントに紐づくトークンの使用は避けてください。

仕様の詳細はGitLab公式の
[Project Access Token](https://docs.gitlab.com/user/project/settings/project_access_tokens/)と
[アクセストークンのscope](https://docs.gitlab.com/security/tokens/access_token_scopes/)を
参照してください。

### 4.2 Webhookと内部コールバックのシークレット

互いに異なるランダム値を2つ生成します。

```bash
openssl rand -hex 32
openssl rand -hex 32
```

1つ目を`GITLAB_WEBHOOK_SECRET`、2つ目を`JENKINS_CALLBACK_TOKEN`に使用します。
値はGitやチャット、スクリーンショットへ残さないでください。

## 5. 環境変数を設定する

サンプルをコピーし、権限を制限してから編集します。

```bash
cp .env.example .env
chmod 600 .env
```

`.env`の少なくとも次の項目を設定します。`JENKINS_USER`と`JENKINS_TOKEN`はJenkinsの
初期設定後に作成するため、この時点では空欄のままで構いません。

```dotenv
GITLAB_WEBHOOK_SECRET=<生成したWebhook用シークレット>
GITLAB_URL=https://gitlab.com
GITLAB_TOKEN=<GitLabアクセストークン>

JENKINS_USER=
JENKINS_TOKEN=
JENKINS_BUILD_JOB=ai-review-build
JENKINS_TEST_JOB=ai-review-test
JENKINS_CALLBACK_TOKEN=<生成した内部コールバック用シークレット>
GITLAB_CREDENTIALS_ID=gitlab-token

# Claude Pro/Maxの対話ログインを使う場合は両方空欄
CLAUDE_CODE_OAUTH_TOKEN=
ANTHROPIC_API_KEY=
```

`.env`は`.gitignore`の対象です。次のコマンドでGitの追跡対象になっていないことを確認
できます。

```bash
git status --short -- .env
```

何も表示されなければ問題ありません。

## 6. イメージをビルドして全サービスを起動する

```bash
./scripts/setup-docker.sh --with-agent
```

この処理はJenkinsとClaude Codeエージェントのイメージをビルドし、Jenkins、専用Docker
daemon、Webhook、worker、DBマイグレーションを起動します。初回はイメージ取得と
ビルドに時間がかかります。

起動状態を確認します。

```bash
docker compose --profile agent ps
```

`jenkins`、`docker`、`webhook`、`worker`が`healthy`になることを確認します。

## 7. Jenkinsを初期設定する

初期解除パスワードを表示します。

```bash
docker compose exec jenkins \
  cat /var/jenkins_home/secrets/initialAdminPassword
```

ブラウザで[http://localhost:8080](http://localhost:8080)を開き、表示したパスワードで解除します。

1. プラグイン選択では追加インストールをスキップします。必要なプラグインはイメージに
   導入済みです。
2. 管理者ユーザーを作成します。
3. Jenkins URLはローカル利用なら`http://localhost:8080/`のまま保存します。

初回起動時に次のPipelineジョブが自動作成されます。

- `ai-review-build`
- `ai-review-test`

### 7.1 Jenkins APIトークンを作成する

Jenkins右上のユーザーメニューから`Security`を開き、`API Token`で新しいトークンを
生成します。表示されたトークンはこの場で保存します。

`.env`へJenkinsユーザー名とAPIトークンを設定します。

```dotenv
JENKINS_USER=<作成したJenkinsユーザー名>
JENKINS_TOKEN=<生成したJenkins APIトークン>
```

### 7.2 GitLab Checkout Credentialを登録する

Jenkinsで`Manage Jenkins` → `Credentials` → `System` → `Global credentials` →
`Add Credentials`を開き、次の値を登録します。

| 項目        | 値                                                  |
| ----------- | --------------------------------------------------- |
| Kind        | Username with password                              |
| Username    | Project Access Token作成時に生成されたBotユーザー名 |
| Password    | `GITLAB_TOKEN`と同じアクセストークン              |
| ID          | `gitlab-token`                                    |
| Description | GitLab checkout token（任意）                       |

IDは`.env`の`GITLAB_CREDENTIALS_ID`と一致させます。Personal Access Tokenを使う場合は、
`Username`へそのGitLabユーザー名を指定します。

### 7.3 更新した環境変数をコンテナへ反映する

`.env`を保存しただけでは起動中のコンテナへ反映されないため、サービスを再作成します。
named volume内のJenkins設定、DB、Claude認証は保持されます。

```bash
docker compose --profile agent up -d --no-build --force-recreate --wait
```

Jenkins API認証を確認します。

```bash
docker compose exec -T webhook sh -c \
  'curl -fsS -u "$JENKINS_USER:$JENKINS_TOKEN" \
  "$JENKINS_URL/crumbIssuer/api/json" >/dev/null'
```

終了コード0で戻れば認証成功です。

## 8. Claude Codeへログインする

Claude Pro/Maxを使う場合は、次を実行します。

```bash
./scripts/claude-login.sh login
```

表示されたURLをWindows側のブラウザで開き、Claude Pro/Maxを契約したアカウントで
認証します。認証後に状態を確認します。

```bash
./scripts/claude-login.sh status
```

`Login method: Claude Pro account`が表示されれば完了です。AI単体の疎通確認も行う場合は
次を実行します。この確認はClaudeの利用枠を消費します。

```bash
docker compose --profile agent run --rm --no-deps worker \
  claude --print --max-turns 1 "OKとのみ回答してください"
```

Anthropic Console APIキーを使う場合はログインせず、`.env`の`ANTHROPIC_API_KEY`へキーを
設定してworkerを再作成します。

```bash
docker compose --profile agent up -d --no-build --force-recreate worker --wait
```

## 9. Flutter CIイメージを準備する

Jenkins専用Docker daemonへ、Build/Lint/Testで使うイメージを取得します。

```bash
docker compose exec -T jenkins \
  docker pull ghcr.io/cirruslabs/flutter:stable
```

`.env`で`CI_IMAGE`を変更した場合は、そのイメージ名を指定してください。

## 10. WebhookをGitLabから到達可能にする

GitLab.comは`127.0.0.1:8000`へ直接接続できないため、別ターミナルでngrokを起動します。

```bash
cd ~/ai-review
./scripts/demo-env.sh ngrok
```

表示されたHTTPS URLを控え、末尾へ`/webhook`を付けます。

```text
https://<ngrok-domain>/webhook
```

ngrokを実行しているターミナルは、AIレビュー中は起動したままにします。無料枠などで
ドメインが変わった場合は、次項のGitLab Webhook URLも更新します。

## 11. GitLab Webhookを登録する

AIレビュー対象プロジェクトの`Settings` → `Webhooks`で次を登録します。

| 項目             | 値                                                |
| ---------------- | ------------------------------------------------- |
| URL              | `https://<ngrok-domain>/webhook`                |
| Secret token     | `.env`の`GITLAB_WEBHOOK_SECRET`               |
| Trigger          | Merge request events                              |
| Trigger          | Note events（Commentsと表示される場合はComments） |
| SSL verification | 有効                                              |

Push eventsは不要です。登録後、GitLabのWebhook画面で直近Deliveryの応答を確認できます。

## 12. AIレビューを動作確認する

1. 対象Flutterプロジェクトで作業ブランチを作成し、差分をpushします。
2. 同じプロジェクト内のブランチからMRを作成します。
3. GitLabのWebhook DeliveryがHTTP 2xxになったことを確認します。
4. Jenkinsの`ai-review-build`でBuildとLintが実行されることを確認します。
5. Build/Lint成功後、MRへAIレビューのDiscussionが投稿されることを確認します。

状態とログは次のコマンドで確認できます。

```bash
./scripts/demo-env.sh status
docker compose --profile agent logs --tail=100 jenkins webhook worker
docker compose logs -f worker
```

MR作成時には利用可能なコマンドの案内も投稿されます。主なコマンドは次のとおりです。

| コマンド           | 動作                                       |
| ------------------ | ------------------------------------------ |
| `/ai review`     | AIレビューを手動実行                       |
| `/ai apply R1`   | 指摘`R1`の修正案を差分表示               |
| `/ai approve R1` | 指摘`R1`の修正をソースブランチへコミット |
| `/ai reject R1`  | 指摘`R1`を却下                           |
| `/ai test`       | テスト生成を手動実行                       |

`/ai`コマンドはDeveloper以上のユーザーだけが実行できます。

## 13. よくある問題

| 症状                        | 確認箇所                                                                       |
| --------------------------- | ------------------------------------------------------------------------------ |
| Webhookが401/403            | GitLabのSecret tokenと`GITLAB_WEBHOOK_SECRET`が一致しているか                |
| Webhookが接続失敗           | ngrokが起動中か、URL末尾が`/webhook`か、古いngrok URLでないか                |
| MR作成後にJenkinsが動かない | `.env`の`JENKINS_USER`/`JENKINS_TOKEN`、webhookログ、Jenkins APIトークン |
| Jenkins Checkoutが失敗      | Credential IDが`gitlab-token`か、ユーザー名とGitLabトークンが正しいか        |
| Build/Lintが失敗            | 対象がFlutter Webプロジェクトか、`CI_IMAGE`と各コマンドが対象に合うか        |
| workerで認証エラー          | `./scripts/claude-login.sh status`、または`ANTHROPIC_API_KEY`              |
| AI結果がMRへ投稿されない    | `GITLAB_TOKEN`の`api` scope、期限、対象プロジェクトでのRole                |

詳細ログを継続表示する場合は次を実行します。

```bash
docker compose --profile agent logs -f jenkins webhook worker
```

## 14. 社内GitLabでの変更点

- `.env`の`GITLAB_URL`を社内GitLabのベースURLへ変更します。
- GitLabサーバーからWebhookホストへ到達できる場合、ngrokは不要です。
- `WEBHOOK_HTTP_HOST=0.0.0.0`へ変更するだけで直接公開せず、リバースプロキシでTLS、
  アクセス制限、必要に応じて送信元IP制限を設定してください。
- 独自CAを使う場合はCA証明書を`jenkins/certs/`へ置き、次を実行します。

```bash
docker compose up -d --force-recreate cert-init jenkins
```

WindowsファイアウォールやWSLのネットワーク方式によっては、ポート転送設定も必要です。

## 15. 停止と再開

停止前にngrokのターミナルで`Ctrl-C`を押します。次にサービスを停止します。

```bash
./scripts/demo-env.sh down
```

次回は次のコマンドで再開できます。

```bash
./scripts/demo-env.sh up
./scripts/demo-env.sh ngrok
```

`docker compose down -v`は、Jenkins設定、DB、Claude認証、CIイメージを含むnamed volumeを
削除します。初期化が目的でない限り実行しないでください。
