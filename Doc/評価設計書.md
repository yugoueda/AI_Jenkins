**バージョン:** 0.1

**作成日:** 2026年8月15日

**対象:** AI Review Jenkins デモ版

**ステータス:** Draft（仕様未決事項の確定後に基準化）

## 1. 目的

本書は、設計書に定義されたユースケースが実際のGitLab・Jenkins・CLIエージェント連携で成立することを、機能、AI出力品質、信頼性、セキュリティ、運用性の観点から評価するための設計を定める。

評価の最終目的は、「MR作成→レビュー→修正→再レビュー→テスト生成・実行→結果確認」の主要フローを、人間の承認境界と安全性を維持したまま完了できると判定することである。

## 3. 評価対象

### 3.1 アクター

| アクター | 主な責務 |
|---|---|
| 開発者（レビュイー） | MR作成、手動修正、AI修正案の確認・承認、DiscussionのResolve |
| レビュアー | AI指摘の妥当性確認、人間指摘、最終Approve |
| GitLab | MR・Discussion・Noteの管理、Webhook通知、コミット受付 |
| Webhook受信サーバ | 認証、イベント振り分け、ジョブ登録、Jenkinsコールバック受付 |
| Jenkins | Checkout、Build、Lint、Test、C0/C1計測 |
| CLIエージェント / Worker | レビュー、修正案、テストの生成とキューの逐次実行 |
| DB | AI指摘、修正パッチ、ジョブ状態の永続化 |

### 3.2 確認したユースケース

| UC ID | ユースケース | 開始条件 | 完了条件 |
|---|---|---|---|
| UC-01 | MR作成後の初回AIレビュー | MR `open/opened` Webhook | Build/Lint成功後にレビュー結果がMRへ投稿される |
| UC-02 | Build失敗時の修正提案 | Buildパイプライン失敗 | Lintと通常レビューを行わず、原因と修正案がMRへ投稿される |
| UC-03 | Lint失敗と手動レビュー | Build成功、Lint失敗 | 失敗が通知され、`/ai review`実行時のみレビューされる |
| UC-04 | AI指摘と人間指摘の確認 | AIレビュー完了または`/review` | 指摘がGitLab上で確認でき、対応単位でResolveできる |
| UC-05 | AI修正案の確認 | `/ai apply <ID>` | 保存済みパッチが未適用の差分として投稿される |
| UC-06 | AI修正案の承認・適用 | `/ai approve <ID>` | 承認したパッチだけがMRソースブランチへコミットされる |
| UC-07 | 指摘の却下または手動修正 | `/ai reject <ID>` または手動push | 対応結果が明確で、Resolve後のフローを阻害しない |
| UC-08 | 全指摘Resolve後の再レビュー | `blocking_discussions_resolved: false→true` | API再確認、Build/Lint再実行、再レビューが順序どおり完了する |
| UC-09 | 再レビューで追加指摘 | 再レビューで指摘あり | 新たな指摘が登録・投稿され、指摘対応へ戻る |
| UC-10 | ユニットテスト自動生成 | 再レビュー指摘なし | テストが生成・コミットされ、Jenkinsテストが起動する |
| UC-11 | ユニットテスト手動生成 | `/ai test` | 自動生成と同じ生成・コミット・実行フローが起動する |
| UC-12 | テスト・カバレッジ結果確認 | Jenkinsテスト完了 | 成否、C0/C1、目標達成可否がMRに投稿される |
| UC-13 | 複数MR・複数ジョブの安全な実行 | 同時または連続Webhook | ジョブが消失・競合せず、定義された順序で終了する |
| UC-14 | システム失敗からの回復 | CLI/API/プロセス失敗 | 1回のリトライまたはFAILED化、MR通知、次ジョブ継続が行われる |
| UC-15 | MR完了・更新後の状態管理 | merge/close/追加push | `Closed`または再レビューへの遷移がMR単位で記録される |

### 3.3 評価範囲外

- GitLab自体、Jenkins自体、Claude Code自体の製品内部品質
- 生成コードに対する業務仕様上の最終判断（人間がApproveする）
- 社内本番ネットワークでのnginx構成、社内CA、大規模負荷（デモ版合格後の本番移行評価で別途実施）
- 未実装のPython / TypeScript / Javaプロジェクトアダプタ

## 4. 評価方針

### 4.1 評価レベル

| レベル | 目的 | 主な実行環境 | 合格の考え方 |
|---|---|---|---|
| L1: ユニット | パーサ、認証、DB遷移、フォーマッタの分岐確認 | `pytest`、SQLite分離DB、API/CLIモック | 全件成功 |
| L2: コンポーネント結合 | Webhook→DB→Worker、Jenkins callback→DBの契約確認 | Docker Compose、fake CLI、GitLab/Jenkins APIスタブ | P0/P1全件成功 |
| L3: 実環境E2E | 実GitLab・Jenkins・Claude Codeを通した業務フロー確認 | デモ用GitLabプロジェクト、Jenkins、Webhook、Worker | P0全件、P1 95%以上成功 |
| L4: AI品質 | 指摘、修正案、生成テストの有用性確認 | 正解付きFlutter評価用MRセット | 7.2の暫定基準を満たす |

### 4.2 優先度

| 優先度 | 定義 | 例 |
|---|---|---|
| P0 | 失敗すると主要フローが完了できない、または無承認修正・機密漏えい・権限逸脱が起き得る | MR→レビュー→テストの完走、パッチ改ざん防止 |
| P1 | 代替運用は可能だが、正しい状態・通知・回復性に影響する | リトライ、状態遷移、カバレッジ未達通知 |
| P2 | 利便性、表示、チューニングに影響する | コメント表示、処理時間の最適化 |

### 4.3 総合合否判定

デモ版の「適合」は以下をすべて満たす場合とする。

1. L1とL2のP0/P1が全件合格し、自動テストに新規回帰失敗がない。
2. L3のP0が全件合格し、P1の成功率が95%以上である。
3. 不正トークン、権限不足、パッチ改ざん時の破壊的な副作用が0件である。
4. L4の基準が合意済みで、評価用MRセットで合格する。
5. 11節のP0未決事項が0件である。
6. 未解決不具合は、影響、回避策、解消予定を記録し、受入判定者が承認している。

## 5. 評価環境とデータ

### 5.1 環境

| 項目 | 要件 |
|---|---|
| GitLab | 専用の評価プロジェクト、Maintainer / Developer / Reporterの3ユーザー |
| Jenkins | `ai-review-build`、`ai-review-test`ジョブ、GitLab Credential、内部コールバックトークン |
| 実行基盤 | `jenkins`、`webhook`、`worker`、DBがDocker Compose上でhealthy |
| CLIエージェント | 実Claude Code認証済み環境と、異常系制御用fake CLIの両方 |
| 時刻 | Jenkins、Webhook、Worker、GitLabの時刻差を1分以内にする |
| ログ | GitLab Webhook delivery、Jenkins console、Webhook/Workerログ、DBスナップショットを保存する |

### 5.2 評価用MRセット

評価用リポジトリに以下の独立したMRを用意する。各MRには正解と期待カバレッジをメタデータとして別管理し、AIには渡さない。

| データID | 内容 | 用途 |
|---|---|---|
| D-01 | Build成功・Lint成功・既知不具合1件 | 標準レビュー、修正、再レビュー |
| D-02 | コンパイルエラー | Build失敗分岐 |
| D-03 | Lintエラーのみ | Lint失敗分岐と手動レビュー |
| D-04 | null、境界値、非同期、状態遷移の既知不具合 | AI指摘品質とテスト生成品質 |
| D-05 | 問題のない差分 | 過剰指摘と指摘なしフロー |
| D-06 | 既存テストあり、C0/C1目標未達 | 追加テストと未達通知 |
| D-07 | テストを1回目だけ失敗させるフィクスチャ | リトライ |
| D-08 | 承認対象外ファイルを含む改ざんパッチ | 整合性と安全性 |
| D-09 | 异なる2つのMRと、同一MRへの連続コマンド | キューと競合防止 |

AI品質の統計評価ではD-04/D-05を拡張し、最低20 MR、重大度別に各カテゴリ5件以上の正解指摘を用意する。

## 7. AI品質評価

### 7.1 指標

| 指標 | 算出方法 | 補足 |
|---|---|---|
| 指摘再現率 | 正解指摘のうちAIが本質的に同じ問題を指摘した件数 / 正解指摘数 | Critical/Highは別集計 |
| 指摘適合率 | 人間レビュアーが有効と判定したAI指摘数 / AI指摘数 | 評価者2名、不一致は協議 |
| 位置精度 | 正しいファイルかつ対象行±5行以内の指摘率 | 差分外の原因は関連関数単位で判定 |
| パッチ適用率 | `git apply --check`に成功した修正パッチ数 / パッチ付き指摘数 | 対象SHA不一致は別集計 |
| 修正正解率 | 対象不具合を解消し、既存テストを壊さないパッチ率 | 未承認パッチは評価ブランチで検証 |
| バグ再現テスト率 | 修正前に失敗し、修正後に成功する生成テスト数 / 対象不具合数 | テスト不能の理由は別記 |
| テスト有効率 | コンパイル可能かつ非フレーキーな生成テスト率 | 各3回実行し、3回同結果を必須とする |
| カバレッジ寄与 | 生成前後のC0/C1の差 | 全体と変更差分を分けて記録 |
| 不要変更率 | 要求外ファイルまたは無関係行を変更した評価数 / 全評価数 | 0件を必須とする |

### 7.2 暫定受入基準

以下は初回評価用の暫定値であり、製品責任者と開発チームの合意後に確定値とする。AIの出力ぶれを考慮し、同一MRを3回独立実行し、2回以上基準を満たした場合にケース合格とする。

| 項目 | 暫定基準 |
|---|---|
| Critical/High指摘再現率 | 100% |
| 全指摘再現率 | 80%以上 |
| 指摘適合率 | 70%以上 |
| パッチ適用率 | 90%以上 |
| 修正正解率 | 80%以上 |
| バグ再現テスト率 | 80%以上 |
| テスト有効率 | 90%以上 |
| 不要変更 | 0件 |
| 機密情報を含む出力 | 0件 |

## 10. 評価実行手順と記録

### 10.1 事前条件

1. `.env`の必須値を設定し、トークン本文は評価証跡に残さない。
2. Jenkinsの2ジョブ、GitLab Checkout Credential、Webhookが正しいことを確認する。
3. 評価開始時のcommit SHA、コンテナイメージdigest、設定値（秘密値を除く）を記録する。
4. DBを評価用に分離し、MRとジョブの開始状態を固定する。
5. L1→L2→L3→L4の順に実施し、上位レベルのP0失敗時は後続評価を保留する。

### 10.2 証跡セット

各評価で以下を1セットとして保存する。

- 評価ID、実行日時、実行者、対象commit SHA、対象MR URL
- 入力条件と予期しない手動操作の有無
- GitLab Webhook payload/delivery ID（トークンはマスク）
- Jenkins build URL、stage結果、console log
- 関連する`findings`と`job_queue`のレコード
- Workerログ、CLI終了コード、入出力ハッシュ（機密情報を除く）
- MRコメント/Discussion、生成commit、C0/C1レポート
- 実績結果、合否、不具合ID、再評価結果

### 10.3 実行記録テンプレート

| 項目 | 記録内容 |
|---|---|
| 評価ID | EV-F-xxx / EV-R-xxx / EV-S-xxx / EV-N-xxx |
| 実行条件 | commit、イメージ、設定、データID |
| 期待結果 | 本書の記載 |
| 実績結果 | 時刻と客観的な出力 |
| 判定 | Pass / Fail / Blocked / Not Run |
| 証跡 | MR、Jenkins、ログ、DB snapshotへの参照 |
| 備考 | 差異、手動操作、不具合ID、再評価日 |

## 12. 終了条件

評価は以下のすべてを満たした時点で終了する。

- 対象とする全評価IDにPass / Fail / Blocked / Not Runのいずれかが記録されている。
- P0は全件Pass、P1は4.3の基準を満たし、合否の根拠証跡を追跡できる。
- AI品質指標は評価データ、モデル名、実行日時、実行回数とともに記録されている。

- 評価完了後にトークン、評価ブランチ、テスト用Webhookなどの後始末が完了している。
